# RUN-037 — Task Plan

## Demand

Cartuchos de domínio plugáveis (pedido do user): provar que um modelo
generalista pode receber "download" direcionado de uma área específica —
virar especialista com o cartucho plugado e voltar a ser generalista sem ele.
Domínio escolhido: **regex Python** (auto-verificável: o regex gerado executa
contra casos de teste — rubrica de execução real, não substring).

## Design

**Tier testado**: LoRA por domínio = "cartridge file" (poucos MB), mescla-se
nos pesos do 0.5B quando plugado (merge em runtime), remove quando desplugado.
Base generalista nunca é sobrescrita. (Tier universal texto+kpack já validado
em RUN-036 — fora do escopo aqui.)

**Protocolo**:
1. BASELINE: aluno BASE (sem cartucho) responde 8 tarefas de regex; cada
   resposta é extraída como pattern e EXECUTADA contra casos de teste
   (compile + match expected) → `base_pass`.
2. Professor (30B, teacher_chat existente) gera ~24 lições do domínio em
   formato estrito {skill,probe,ideal_answer,expected_tokens} — mesmo
   harness de JSON de convdistill.
3. Aluno treina **LoRA r=8** (adapters em attn+mlp, ~3-4M params) nas lições —
   base congelada. merge_lora() só no artifact final.
4. EVAL PLUGADO: mesma eval de 8 tarefas com cartucho ativo → `plugged_pass`.
5. EVAL DESPLUGADO: cartucho removido → `unplugged_pass` + ppl_neutral
   (generalista intacto?).

**Métrica central**: plugged_pass vs base_pass (ganho de domínio) +
unplugged_pass≈base_pass + ppl_neutral estável (reversibilidade).
Cartridge size em MB = custo do "download".

## Branch

`main` — convenção do projeto; aditivo (script+artifacts+docs).

## Tasks

### T1 — `scripts/domcart.py`

**Domain**: mixed | **Risk**: medium | **Status**: pending

Reusa teacher_chat/render_chat/LoRA de convdistill.py (import ou copiar).
Driver: baseline eval (exec-based) → coleta lições → LoRA SFT → eval
plugado/desplugado → escreve `artifacts/domcart/{metrics.jsonl,
cartridge_regex.pt, pack_regex.json}`. Env: DOMAIN, LESSONS, LORA_R, LR.

**Acceptance**: compile OK; cartridge carrega em modelo base; metrics
tem base/plugged/unplugged pass + ppl_neutral ×3.

### T2 — domain eval set

**Domain**: data | **Risk**: low | **Status**: pending

8 tarefas regex com casos de teste determinísticos embutidos no script:
{task_prompt, tests: [(input_string, expected_match_bool_or_group)]}.
Execução em sandbox subprocess com timeout (regex pode dar ReDoS).

**Acceptance**: eval roda standalone contra um answer fixo de exemplo.

### T3 — execução plug/unplug

**Domain**: automation | **Risk**: medium | **Status**: pending

Teacher :8089 config campeã; ROUNDS=24 lições; eval execução real;
registrar MB do cartucho.

**Acceptance**: metrics.jsonl completo com plugged/base/unplugged +
tamanho do cartucho em bytes.

### T4 — docs

**Domain**: docs | **Risk**: low | **Status**: pending

SESSION_HANDOFF.md + artifacts/report.md: pass rates, delta, reversibilidade,
tamanho do download, veredito "é possível?" com número.

## Contract

**Scope in**: `scripts/domcart.py`, `artifacts/domcart/`,
`SESSION_HANDOFF.md`, `artifacts/report.md`, `.agentic/` state.

**Scope out**: `vendor/`, `src/ncm_swe/`, `~/models/qwen05-sft` (read-only —
cartridge é arquivo separado), `artifacts/convdistill/` (read-only import).

**Quality gates**:
- `python -m py_compile scripts/domcart.py`
- exec-rubric sandboxed (timeout 5s/pattern; sem exec na thread principal)
- baseline eval gravada ANTES do treino
- `git diff --check`; `git status` restrito ao scope

**Acceptance criteria**:
1. pass rates base/plugged/unplugged com N=8 e números salvos
2. cartucho persiste em arquivo separado + tamanho registrado
3. unplugged_pass + ppl_neutral evidenciam reversibilidade
4. docs com números reais (incluindo resultado nulo/negativo)

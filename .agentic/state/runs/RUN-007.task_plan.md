# RUN-007 Task Plan — Rascunho especulativo hierárquico (NCM×spec-decode)

Contexto: `scripts/train_level_heads.py` confirma que as heads atuais
preveem códigos do **próximo token** (t+1) a partir do hidden da última
posição. Para propor *blocos* de k tokens a partir de **um** forward do
backbone (única forma do draft não precisar de forward por posição),
precisamos de heads por offset estilo Medusa: `feat_j = h[:, -1-j]`
prevê o token final → offset j+1. Um único forward do backbone produz
todos os k features — custo de treino igual ao atual. Rascunho em
tempo de inferência: heads offset-j propõem token t+1+j (via códigos
grossos l0/l1 → nearest-embedding); uma forward de verificação valida o
bloco inteiro; aceita prefixo casado. Sem interferir no llama-server do
usuário.

## Branch Strategy

- decision: `current_branch` (`main`).

## Phases

- Phase 1: T001 | Phase 2: T002 (treino, background) | Phase 3: T003, T004

## Tasks

### T001 — Heads multi-offset no trainer (`--offsets K`)

**Intent**: estender `train_level_heads.py` com flag `--offsets K`
(default 1 = comportamento atual). Com K>1, um forward sobre
`ids[:, :-1]` produz features `h[:, -1-j]` para j=0..K-1; cada offset
tem seu próprio `LevelHeads` prevendo códigos do token final
(`ids[:, -1]`). Log por offset (`off0`, `off1`…) e checkpoint
resume-capable em subdir separado do out de nível único.
**Domain**: ml | **Risk**: low | **Deps**: []
**Acceptance**: `--offsets 4` treina 4 conjuntos de heads do mesmo
forward; `off0` reproduz loss l0≈0.9 do run anterior (sanidade);
semântica documentada no docstring.

### T002 — Treinar block-heads (offsets 0..3)

**Intent**: treinar com `--offsets 4 --steps 1500` sobre o stream Qwen
cacheado (1,41M tokens), saída `artifacts/block_heads_qwen05/`,
`--resume` ativo. Registrar losses finais por offset no execution
report — espera-se degradação com o offset (medida real da qualidade do
rascunho).
**Domain**: ml | **Risk**: low | **Deps**: [T001]
**Acceptance**: `final.pt` existe com K=4 conjuntos; loss final por
offset registrado; treino ≤ ~3h na ThinkPad.

### T003 — `scripts/spec_pyramid.py`: draft de bloco + verificação

**Intent**: implementar geração especulativa: (a) forward AR sobre
contexto → logits + hidden; (b) offsets 1..K propõem tokens por
nearest-embedding sobre códigos previstos (nível l0 só, ou l0+l1 se
confiança baixa — flag `--depth`); (c) um forward de verificação sobre
o bloco de K drafts; (d) aceitar maior prefixo casado com o argmax AR,
sempre avançando ≥1 token (correção garantida pelo próprio verify).
Comparar `--mode spec` vs `--mode ar` em mesmo prompt/seeds/ctx.
Persistir `artifacts/spec_pyramid_bench.json` com: acceptance por
offset, mean tokens/forward, tok/s ambos modos.
**Domain**: ml | **Risk**: low | **Deps**: [T002]
**Acceptance**: spec mode idêntico ao AR token-a-token (mesmo output
greedy — verificação por argmax garante); acceptance reportada por
offset; tok/s medido nos dois modos.

### T004 — Report honesto

**Intent**: adicionar seção em `artifacts/report.md`: acceptance por
offset, tokens/forward, speedup (ou slowdown) real, e interpretação —
se acceptance baixa, dizer o que falta (heads mais profundas? mais
treino? offsets menores?). Atualizar execution/compliance artifacts.
**Domain**: docs | **Risk**: low | **Deps**: [T003]
**Acceptance**: números do report batem com `spec_pyramid_bench.json`;
resultado negativo, se for o caso, documentado sem maquiagem.

## T004 — decode_pyramid.py + bench adaptativo (resultado: negativo parcial, informativo)

`scripts/decode_pyramid.py` escrito: reconstrói FrozenQwen+LevelHeads do
`train_level_heads.py`, decodifica por posição (heads l0→l5 greedy,
reconstrução ∑códigos → argmin sobre embeddings = token), baseline AR
nativo (argmax feat@Eᵀ — mesmo backbone, controle honesto).

`artifacts/pyramid_bench.json` (prompt "def fibonacci(n):", n=16):
| modo | tok/s | níveis médios | agree c/ argmax |
|---|---|---|---|
| AR | 3,65 | — | 1,00 (sanidade) |
| fixed 6 níveis | 2,42 | 6,0 | 0,00 |
| adaptive τ=0,3 | 2,48 | 5,7 | 0,00 (1 posição saiu c/ 1 nível) |
| adaptive τ=0,6/0,9 | ~2,5 | 6,0 | 0,00 |

**Leitura honesta**:
1. **Pirâmide 1-posição-por-vez perde ~34% para AR** — o forward do backbone
   domina; heads+argmin são overhead. O speedup NCM real medido antes
   (2,27× em 471M) vem de *menos passagens sequenciais no backbone*, não
   de decodificação por códigos.
2. **agree=0,00** — erro composto (heads finos l5~4,0 × recuperação do
   codebook 32%) ⇒ token exato quase nunca. Posições com código denso ok,
   raro sair o token "certo". Limitação real, não bug (AR self-agree=1,0).
3. **Knob adaptativo existe e tem distribuição**: min(confs) sobre níveis
   usados é conservador demais; τ=0,3 já captura posições "fáceis" que
   resolvem no nível grosso. Refinamento futuro: margem sobre candidatos
   a token, não prob. de código.
4. **Direção que os dados apontam**: l0 barato + razoavelmente certo
   (loss 0,94, ~39% top-1) ⇒ a cabeça grossa é candidata natural a
   *draft* de blocos para verificação AR (spec-decode "piramidal") — a
   composição que junta nosso NCM com o caminho MANA.

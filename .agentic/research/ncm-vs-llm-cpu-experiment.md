# NCM (Next-Concept Modeling) on conventional hardware — reuse of Qwen training

## Context
User wants an experiment in the spirit of `../colibri` (Go+cgo BF16 CPU inference
of Qwen3-Coder-30B via NVMe streaming): train a model using the new **NCM**
paradigm — Stanford HazyResearch + Together AI, arXiv 2610.14162 (Oct 2026) —
on a conventional machine, reusing Qwen(-Coder) training where possible, aiming
"well above ordinary". NCM = multiscale residual VQ-VAE text tokenizer +
transformer that generates discrete-code levels coarse→fine, all codes within a
level in parallel (K sequential passes total instead of L tokens). Reported
9–31× faster than diffusion baselines at ~100M–725M scale; beats AR+diffusion
on Sudoku. This maps directly onto colibri's core finding: CPU LLM inference is
memory-bandwidth-bound — NCM trades sequential weight reads for parallel
compute, the exact bottleneck this machine has.

## Constraints
- Hardware: i5-1235U (12 threads), 23 GiB RAM (~10 free), 27 GiB swap, 106 GB
  free disk, **no GPU** (Intel Iris Xe only). torch 2.15.0+cpu venv exists at
  `/tmp/llmenv`; CPU training already proven (colibri self-improve loop:
  Qwen2.5-Coder-0.5B SFT 38%→78.6% on 42 PT-BR code tasks).
- Official NCM repo (MIT): `github.com/HazyResearch/ncm` ships eval code
  (`models/`, `tokenization/`) and HF checkpoints (XSum, WMT14, Sudoku, LM1B
  s/m/l, TinyStories, OpenWebText) — **no training code released**. VQ-VAE and
  generator training must be implemented locally (can reuse their model
  definitions as reference).
- Local weights: `/home/kron/models/Qwen3-Coder-30B-A3B-Instruct-UD-Q3_K_XL.gguf`
  (13 GB, llama.cpp-usable teacher — the "full" Qwen3-Coder), `Qwen3-0.6B-Q8_0.gguf`
  (610 MB); `/tmp/llm/qwen05` (Qwen2.5-Coder-0.5B) + `/tmp/llm/qwen15` (1.5B) HF
  dirs. colibri `.models/` is empty (safetensors removed); restoring the 61 GB
  BF16 is possible but costly and not required for teaching.
- ncm_swe is not a git repo yet; only agentloop scaffolding exists.
- NCM known limits (paper/independent repro): fixed output length per
  tokenizer config, no streaming, occasional name/number swaps, batch>64 loses
  to AR serverside, scale unproven past ~725M.

## Options
- **A. From-scratch NCM on open corpus** (TinyStories/LM1B tokenized datasets
  on HF): faithful repro, but generic English LM — ignores "reuse Qwen" and
  weakly differentiated result.
- **B. NCM for code/PT-BR distilled from Qwen** — train own residual VQ-VAE on
  a corpus generated/existing for the target domain (PT-BR + code), then train
  the level-parallel generator. Teacher corpus from Qwen2.5-Coder-1.5B (fast,
  local) with optional high-value samples from the 30B GGUF via llama.cpp.
  Matches colibri's distillation culture; unique result: first CPU-trained NCM
  for a code-ish domain.
- **C. Warm-start NCM generator from Qwen transformer blocks** (0.5B/1.5B/0.6B
  checkpoint → attention/MLP init, new code-embedding + level heads): maximal
  "aproveitar treinamento", risk: shape/objective mismatch adds complexity.
- **D. Hybrid B+C** — recommended.

## Recommendation
**Option D, staged**: (1) implement/trainable NCM in PyTorch-CPU (residual
VQ-VAE + VAR-style generator, referencing HazyResearch model code); (2) corpus =
PT-BR/code instruction data seeded from `colibri/distill/seed_ptbr.jsonl` style,
bulk-generated by Qwen2.5-Coder-1.5B, with a capped 30B-GGUF pass for quality
head ("full" teacher within time budget); (3) train VQ-VAE → freeze → train
generator both from-scratch and warm-started from Qwen2.5-Coder-0.5B blocks;
(4) benchmark vs a parameter-matched AR baseline on tok/s + task accuracy on
this CPU. Deliverable: trained NCM checkpoint + measured NCM-vs-AR speedup
and quality on conventional hardware — a publishable-scale result if NCM's
bandwidth advantage reproduces off-GPU.

## Open Questions
- Corpus scale the user accepts (hours of teacher generation?) — spec proposes
  ~1–5 M tokens v1 with expansion hooks.
- Exact warm-start mapping (Qwen hidden sizes differ per level widths) —
  resolved during implementation; fallback = from-scratch.
- Fixed output length acceptable for v1? (NCM constraint; mitigate via padded
  task format / length conditioning).
- Whether to vendor (MIT) the HazyResearch model/tokenizer code or write clean
  implementation — spec proposes vendor-with-attribution for fidelity.
